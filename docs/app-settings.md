# Web版の設定・アプリ更新

2026-11-25。本人の依頼で、ヘッダーに「設定」を追加する。今回はWebアプリ内の説明・設定を整える範囲で、App Storeへの申請やiPhoneアプリ化は行わない。運営者名と問い合わせ先は、本人の指定により項目だけ設けて空欄にする。

## 画面

- 「アプリを最新版に更新」：現在の版を表示し、公開中の新しい版を検証して同じ画面で再読み込みする。表示中のタブのデータを読み取る、既存の「更新」と区別する。
- ヘルスケア連携の設定：元のタブや編集中のメモを消さずに、既存の連携設定を開く。連携OFFもここから行える。端末に登録済みのShortcutはアプリ更新では書き換えられず、修正版を追加する必要があると説明する。
- プライバシー・データ管理：`privacy.html` と `support.html`。端末とGoogle側の保存、Health4項目の送信/用途、10分の一時保管と取り込み後の記録を区別、連携停止と既存記録保持、論理削除と完全削除を説明する。問い合わせ窓口や完全消去機能を架空で作らない。

## 更新の流れと保護

`js/settings/ui.js` はダイアログと進捗表示、`updater.js` は配信確認、`safety.js` は再読み込み前の記録保護を担当する。

1. nonce付きのversion.jsonをネットワークから読み、版・同一配信先の相対パス・SHA情報を検証する。古い版へ戻す処理はしない。最新版なら再読み込みしない。
2. メモ詳細や他の編集ダイアログ、API保存・写真処理・Healthの未完了要求、未送信キューがある場合は再読み込みを止める。設定ダイアログで背面入力を防ぎ、入力確定待ちとAPI/写真の処理全体のbusyを確認する。
3. 全配信資産のSHAとindexの版を検証する。キャッシュから古い版情報を出して成功扱いしない。
4. Service Workerを更新し、active workerから返る版が期待版になるまで有限時間待つ。workerは全資産を検証し、新しい静的キャッシュを完成させてから有効になる。
5. 最後にもう一度保存状況を確認して、同じアプリ画面を再読み込みする。メタ情報に含まれた別URLへ移動しない。Service Worker非対応の環境は、資産検証後の同一画面再読み込みを使う。

localStorage、IndexedDB schema1/outbox、連携キー、個人の記録、添付キャッシュ`sth-att`は削除・再作成しない。更新ボタンから未送信を勝手に捨てたり、全日更新したりしない。未送信がある場合は記録を残して同期完了後の再試行を案内する。保存状況が読めない場合も更新を止める。

## 静的キャッシュと版の生成

`build/cache-bust.sh` はindexの資産URL、`app-build`メタ情報、SWのBUILD_VERSIONをそろえ、最後に`build/write-version.py`を実行する。version.jsonは実行に必要な静的ファイルだけのSHAを持ち、利用者の記録やキーを読まない。配信対象を変更したら、コードが完成してから再生成する。

SWはversion情報と更新検証GETをnetwork-onlyにし、通常のアプリ資産は検証済みの現行キャッシュを優先する。新しい配信の不一致や通信失敗で旧版の資産を混在させない。インストールが完了するまでは旧版を維持する。完成後に旧い`system-techo-v3-*`静的キャッシュだけを整理し、添付や他用途のキャッシュは保持する。JS/CSSの版付きURLとrootも事前保存し、切替直後の通信断に備える。

初めてこの設定機能を配信した時だけは、古い画面には設定ボタンがないため、本人がアプリを開き直して新しい画面を取得する必要がある。その後の版は設定内から確認・適用できる。iPhone実機でのPWA更新挙動は、隔離Chromeでの確認とは区別する。

## App Storeについて

Appleの[プライバシー要件](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage)と[Health情報の要件](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)を参照して、現在のWeb版で実態に合う説明を追加した。これはApp Storeへの準拠完了や審査承認を意味しない。

現在の一般記録APIは利用者別の認証・保存分離を備えない個人用構成で、Healthキーは一時受渡しだけを保護する。一般配布前は認証・権限・利用者分離・機微情報保護を別工程で実装する。運営者/サポートの実値、保持/完全削除の運用、[App Store Connectのプライバシー申告](https://developer.apple.com/app-store/app-privacy-details/)、ネイティブ権限・Privacy Manifest、申請素材も別途必要。PWAのmanifest.jsonはAppleのPrivacy Manifestではない。

将来のStore配布版の機能コード更新は、[Apple 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)に照らして設計する。今回のWeb版更新ボタンを、そのまま審査外でネイティブ機能を更新できる仕組みとは説明しない。利用規約への同意や全記録消去のボタンを、要件を確認せず追加しない。
